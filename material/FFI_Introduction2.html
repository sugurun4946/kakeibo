Flutter × C++ FFI ガイド
【実践・メモリ管理編】

前編では、数値のキャッチボール（スタックの動き）を学びました。後編となる本書では、家計簿アプリに必須となる「文字列（品目名やメモ）」をやり取りするときのディープな裏側を解説します。

1. 文字列（String）を渡すときの裏側

Dartの "リンゴ" という文字列をC++に渡すとき、数値のようにそのまま投げることはできません。なぜなら、C++はDartの「Stringオブジェクト」の構造を知らないからです。

そのため、FFI通信を行うときは、一度データを「C言語スタイルの文字列（utf8でエンコードされたバイト配列の先頭住所）」に変換する必要があります。

// パソコンのメモリ（ヒープ倉庫）の内部イメージ
0x00FF10A0: ['リ', 'ン', 'ゴ', '\0'] <-- Dartが倉庫に確保したデータ

DartはC++の関数に対して、文字列そのものではなく「0x00FF10A0」という『住所（ポインタ）』を1個だけスタック経由で渡します。C++側は、受け取った住所を const char* item_name として読み込み、末尾の \0（ヌル文字）に到達するまで文字をスキャンします。

2. FFI最大の罠：メモリの自動管理（GC）との衝突

Flutter（Dart）には、使わなくなったメモリを自動で掃除してくれる便利な仕組み「ガベージコレクション（GC）」があります。しかし、これがC++と連携するときに最悪のバグを引き起こします。

🚨 恐怖のクラッシュ（ダングリングポインタ）

発生の流れ：

  1. Dartがヒープ倉庫に "リンゴ" を作り、C++に「住所は 0x00FF10A0 だよ」と教える。
  2. C++がその住所にアクセスして処理を始める直前に、Dart側で「よし、この文字列はもう画面で使わないから掃除しちゃおう」とGCが走り、倉庫の中身を消去（解放）してしまう。
  3. 何も知らないC++が 0x00FF10A0 を覗きに行く。

結果： 存在しない、あるいは全く別のデータが書き込まれたメモリをC++が触った瞬間、OSが危険を検知し、アプリを警告なしで強制終了（セグメンテーションフォルト）させます。

🚨 メモリリーク（メモリの食い尽くし）

上記のクラッシュを防ぐために、DartのFFIには「C++の処理が終わるまで、手動でメモリを固定し、勝手に消さないでね」と命令する仕組み（malloc や toNativeUtf8()）があります。

しかし、手動で確保したメモリは、処理が終わった後に手動で malloc.free() を呼ばない限り、アプリが終了するまでPCのメモリ居座り続けます。 これを放置すると、アプリを動かせば動かすほどパソコンのメモリがガリガリ削られていく「メモリリーク」が発生します。

3. 今後の Day 6 / Day 7 で書く実際のコードイメージ

このメモリの動きをコントロールするために、これから以下のようなDartコードを書いていくことになります。

// 1. Dartの文字列を、手動で「C言語の倉庫（メモリ）」にコピーする
final ffi.Pointer<pkg.Utf8> charPointer = "リンゴ".toNativeUtf8();

try {
  // 2. C++の関数に「倉庫の住所」を渡して実行する
  c_add_expense_bridge(charPointer, 1000);
} finally {
  // 3. 【最重要】C++の処理が終わったら、手動で倉庫を空にする（解放）
  // これを忘れるとメモリリーク、忘れて早く消しすぎるとクラッシュする！
  pkg.malloc.free(charPointer);
}

4. 初心者へのアドバイス

C++単体で動かしていたときは、std::string が裏側で自動的にメモリの確保と解放をやってくれていました。しかし、FFIという国境を渡るときだけは、人間がパスポート（ポインタ）の発行と破棄を手動で管理しなければならない、という点だけ覚えておけば、これからの実装で迷うことはなくなります！
